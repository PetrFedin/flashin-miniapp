# FLASHIN — восстановление failed BusinessEvent в пилоте

## Назначение

BusinessEvent после 10 неуспешных попыток переводится в `failed` и больше не обрабатывается автоматически. Это защищает worker от бесконечного poison-message цикла, но требует управляемого действия оператора.

Recovery-контур хранит отдельно от события:

- последнюю ошибку и время попытки;
- время перехода в terminal `failed`;
- число ручных replay;
- администратора и время последнего replay;
- время успешного разрешения после повторного запуска.

## Консоль Admin

В FLASHIN Admin доступен раздел **BusinessEvent recovery**. Он предназначен для оператора пилота и не требует ручных HTTP-запросов или доступа к базе данных.

Раздел показывает:

- количество событий в `failed`, `pending` и `processed`;
- время самой старой необработанной terminal-ошибки;
- список событий с типом, aggregate, числом автоматических попыток и ручных replay;
- последнюю сохранённую ошибку;
- исходный payload только в карточке выбранного события;
- историю replay и время успешного разрешения `resolved_at`.

После подтверждённого replay консоль переключается на общий список, оставляет событие открытым и обновляет данные каждые 30 секунд. Оператор видит переход `pending` → `processed` либо повторное возвращение в `failed`.

## API диагностики

```http
GET /api/platform/admin/events/summary
GET /api/platform/admin/events?status=failed&limit=100
GET /api/platform/admin/events/{event_id}
```

Доступ на чтение требует admin permission `orders.read`.

Карточка события возвращает исходный payload только в detail endpoint. Список не дублирует payload, чтобы не раздувать ответ и не раскрывать лишние данные в массовой выдаче.

## Replay

В Admin оператор указывает обязательную причину и выполненное исправление. При необходимости можно передать исправленный payload как JSON-объект. Перед отправкой интерфейс показывает отдельное подтверждение о возможном внешнем webhook.

Эквивалентный API-вызов:

```http
POST /api/platform/admin/events/{event_id}/replay
Content-Type: application/json
Authorization: Bearer <admin-token>

{
  "reason": "Исправлено сопоставление webhook destination",
  "payload": {
    "order_id": 123,
    "status": "paid"
  }
}
```

`payload` необязателен. Без него повторно используется сохранённый payload. Если сохранённый JSON повреждён или имеет неверный тип, replay без исправленного payload отклоняется.

Replay требует permission `orders.write` и разрешён только для статуса `failed`.

## Гарантии

- строка BusinessEvent блокируется `FOR UPDATE`;
- два параллельных replay не могут одновременно вернуть событие в очередь;
- `processed` и уже `pending` события не переотправляются;
- Admin блокирует повторный клик и использует dedupe key для mutation-запроса;
- попытки текущего цикла сбрасываются в 0, число ручных replay увеличивается отдельно;
- внешний webhook не вызывается из Admin API;
- событие возвращается в `pending` и обрабатывается штатным worker;
- действие записывается в admin audit log вместе с причиной и состоянием до replay;
- при успешной обработке recovery state получает `resolved_at`.

## Процедура оператора

1. Открыть в Admin раздел **BusinessEvent recovery** и фильтр **Требуют вмешательства**.
2. Выбрать failed event и прочитать `last_error`.
3. Проверить event type, aggregate и исходный payload.
4. Устранить первопричину: destination, mapping, конфигурацию или данные.
5. Не менять payload без подтверждения бизнес-смысла события владельцем процесса.
6. Указать конкретную причину replay и выполненное исправление.
7. При необходимости вставить исправленный JSON-объект payload.
8. Подтвердить один replay.
9. Проверить переход `pending` → `processed` и появление `resolved_at`.
10. Проверить ровно один ожидаемый webhook outbox/destination result.
11. При повторном `failed` остановить replay и передать событие разработчику.

## STOP-критерии

Нельзя выполнять replay, если:

- причина ошибки не устранена;
- событие связано с оплатой или возвратом, а сумма и валюта не сверены;
- payload приходится менять без подтверждения владельца процесса;
- destination уже мог выполнить внешний side effect;
- нет понимания, является ли downstream операция идемпотентной;
- оператор намерен последовательно повторить несколько failed events без индивидуальной проверки.

Webhook delivery остаётся at-least-once относительно аварии процесса после внешнего side effect и до фиксации результата в БД. Stable event ID и idempotency на стороне получателя обязательны для критических интеграций.
