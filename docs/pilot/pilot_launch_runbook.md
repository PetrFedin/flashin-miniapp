# FLASHIN — runbook пилотного запуска

## Принцип допуска

Пилотные пользователи допускаются только после двух последовательных решений **GO**:

1. `make readiness-gate` — проверка конфигурации и готовности до выкладки.
2. `make pilot-gate` — проверка реально работающих публичных Mini App, Admin и API после выкладки.

Любой критический сбой означает **NO-GO**. Нельзя заменять решение gate устным подтверждением или фактом, что контейнеры запущены.

## Обязательные входные данные

До запуска должны быть заполнены и проверены:

- production `.env` без пустых значений и шаблонных секретов;
- реальные Telegram Bot, YooKassa, MoySklad, R2/S3 и Meilisearch параметры;
- DNS и HTTPS для `mini.flashin.store`, `admin.flashin.store`, `api.flashin.store`;
- финальные реквизиты продавца, контакты поддержки и адрес возврата;
- финальные оферта, политика конфиденциальности и правила возврата;
- ответственные за платежи, заказы, склад, поддержку и технический инцидент;
- рабочий канал эскалации и доступ к rollback/backup.

Автоматический gate выявляет шаблонные юридические тексты, но не заменяет юридическое и бизнес-утверждение содержания.

## Последовательность запуска

```bash
# 1. Подготовить production-конфигурацию
cp .env.production.example .env
# заполнить реальные значения

# 2. Получить predeploy GO
make readiness-gate

# 3. Выполнить безопасную выкладку
make deploy-prod

# 4. Проверить публичный контур после DNS/HTTPS
make pilot-gate

# 5. Подготовить контрольные сценарии
make pilot-sheet
make pilot-runner
```

Production deploy выполняет проверку конфигурации, сборку, проверку единственной Alembic head, аудит транзакционной целостности, backup существующей БД, миграции, запуск сервисов, ожидание `/ready`, настройку поиска и внутренний smoke.

## Критерии GO перед первым заказом

- API `/ready` возвращает 200 и подтверждает актуальную схему БД.
- Mini App, Admin и каталог доступны по публичным HTTPS URL.
- В production наружу опубликованы только Caddy 80/443; PostgreSQL, API, Admin, Meilisearch и workers не имеют host ports.
- Admin использует сильный пароль и настроенный TOTP.
- YooKassa создаёт тестовый платёж, webhook меняет заказ ровно один раз.
- MoySklad синхронизирует SKU/варианты/остатки без неизвестных маппингов.
- Notification worker и scheduler работают, не создавая повторных отправок и параллельных запусков одного job.
- Backup создан и доступен; известна команда rollback.
- Юридические документы и реквизиты утверждены ответственным лицом.

## Контрольный пилот: 20 заказов

Первые 20 заказов проводятся не массово, а управляемыми волнами:

1. **Заказы 1–3:** один SKU, один размер, успешная оплата, ручная сверка заказа/платежа/остатка/уведомления.
2. **Заказы 4–7:** разные способы доставки, промокод, бонусы, повторный webhook.
3. **Заказы 8–12:** несколько позиций, пограничный остаток, отмена неоплаченного заказа, поздний платёж.
4. **Заказы 13–16:** частичный и полный возврат денег, ручной review аномалии провайдера.
5. **Заказы 17–20:** обычный клиентский поток без вмешательства разработчика, обработка оператором по SOP.

После каждого заказа фиксируются:

- order ID и payment/refund ID;
- сумма заказа, скидка, бонусы и доставка;
- изменение остатка;
- статусы заказа, платежа, доставки и возврата;
- полученные уведомления;
- записи audit trail;
- фактическое время прохождения этапов;
- ошибка, решение и ответственный, если было отклонение.

## Немедленный STOP пилота

Пилот останавливается при любом из событий:

- один платёж привязан к двум заказам или один заказ оплачен повторно;
- сумма/валюта YooKassa не совпадает с заказом;
- отрицательный остаток или двойное списание/возврат товара;
- возврат денег выполнен без устойчивого локального статуса;
- потерян webhook, notification или business event без видимого retry/review;
- `/ready` возвращает не 200;
- недоступен Admin либо нет audit trail для критического действия;
- обнаружена публикация секрета, персональных данных или внутреннего порта;
- rollback/backup недоступны.

После STOP новые заказы не принимаются до фикса, повторного полного CI и нового решения `make pilot-gate` = **GO**.

## После 20 заказов

Переход к расширенному пилоту возможен только после сверки:

- количество заказов = количество ожидаемых платежей;
- сумма успешных платежей = сумма оплаченных заказов минус подтверждённые возвраты;
- остатки локальной системы согласованы с MoySklad;
- все review cases имеют владельца и решение;
- критических инцидентов нет, некритические имеют срок исправления;
- ответственные за бизнес, операции и технологию подписали acceptance sign-off.
