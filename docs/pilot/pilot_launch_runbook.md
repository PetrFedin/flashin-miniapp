# FLASHIN — runbook пилотного запуска

## Принцип допуска

Пилотные пользователи допускаются только после двух последовательных решений **GO**:

1. `make readiness-gate` — проверка конфигурации и готовности до выкладки.
2. `make pilot-gate` — проверка реально работающих публичных Mini App, Admin и API после выкладки.

Любой критический сбой означает **NO-GO**. Нельзя заменять решение gate устным подтверждением или фактом, что контейнеры запущены.

## Обязательные входные данные

До запуска должны быть заполнены и проверены:

- production `.env` без пустых значений и шаблонных секретов;
- реальные Telegram Bot, YooKassa, MoySklad, R2/S3 и Meilisearch параметры;
- DNS и HTTPS для `mini.flashin.store`, `admin.flashin.store`, `api.flashin.store`;
- финальные реквизиты продавца, контакты поддержки и адрес возврата;
- финальные оферта, политика конфиденциальности и правила возврата;
- ответственные за платежи, заказы, склад, поддержку и технический инцидент;
- рабочий канал эскалации и доступ к rollback/backup.

Автоматический gate выявляет шаблонные юридические тексты, но не заменяет юридическое и бизнес-утверждение содержания.

## Последовательность запуска

```bash
# 1. Подготовить production-конфигурацию
cp .env.production.example .env
# заполнить реальные значения

# 2. Получить predeploy GO
make readiness-gate

# 3. Выполнить безопасную выкладку
make deploy-prod

# 4. Проверить публичный контур после DNS/HTTPS
make pilot-gate

# 5. Подготовить и открыть исполняемый контроль пилота
make pilot-sheet
make pilot-runner
```

Production deploy выполняет проверку конфигурации, сборку, проверку единственной Alembic head, аудит транзакционной целостности, backup существующей БД, миграции, запуск сервисов, ожидание `/ready`, настройку поиска и внутренний smoke.

## Исполняемый контроль 20 заказов

`make pilot-runner` создаёт `docs/pilot/live_pilot_state.json`, а затем при повторных вызовах показывает текущее решение. Markdown-сводка автоматически записывается в `docs/pilot/live_pilot_summary.md`.

После каждого сценария оператор фиксирует фактические идентификаторы, суммы, валюту, изменение остатка и ссылки на доказательства. Пример успешного первого сценария:

```bash
make pilot-record ARGS='\
  --number 1 \
  --result pass \
  --order-id order-123 \
  --payment-id payment-456 \
  --order-status paid \
  --payment-status succeeded \
  --expected-amount 12900.00 \
  --provider-amount 12900.00 \
  --currency RUB \
  --provider-currency RUB \
  --stock-before 5 \
  --stock-after 4 \
  --expected-stock-delta 1 \
  --evidence admin/order-123 \
  --evidence yookassa/payment-456'

make pilot-status
```

Для сценариев повторного webhook/callback обязательно указываются `--webhook-deliveries` и `--domain-effects`. Доменный эффект должен быть ровно один.

Финальное решение формируется только отдельной строгой командой:

```bash
make pilot-final
```

Коды завершения:

- `0` — текущий статус рассчитан без STOP либо финальное решение равно GO;
- `1` — финальная проверка завершилась NO-GO;
- `2` — обнаружено условие немедленного STOP.

Состояние пишется атомарно. Сброс существующего пилота разрешён только осознанной командой `python3 scripts/pilot_control.py init --force`; обычный запуск не перезаписывает накопленные доказательства.

## Критерии GO перед первым заказом

- API `/ready` возвращает 200 и подтверждает актуальную схему БД.
- Mini App, Admin и каталог доступны по публичным HTTPS URL.
- В production наружу опубликованы только Caddy 80/443; PostgreSQL, API, Admin, Meilisearch и workers не имеют host ports.
- Admin использует сильный пароль и настроенный TOTP.
- YooKassa создаёт тестовый платёж, webhook меняет заказ ровно один раз.
- MoySklad синхронизирует SKU/варианты/остатки без неизвестных маппингов.
- Notification worker и scheduler работают, не создавая повторных отправок и параллельных запусков одного job.
- Backup создан и доступен; известна команда rollback.
- Юридические документы и реквизиты утверждены ответственным лицом.

## Контрольный пилот: 20 заказов

Первые 20 заказов проводятся не массово, а управляемыми волнами:

1. **Заказы 1–3:** один SKU, один размер, успешная оплата, ручная сверка заказа/платежа/остатка/уведомления.
2. **Заказы 4–7:** промокод, бонусы, повторный webhook и отмена неоплаченного заказа.
3. **Заказы 8–12:** несколько позиций, пограничный остаток, поздний платёж, support и fulfillment.
4. **Заказы 13–20:** частичный/полный возврат, повторный callback, ручной review, конфликт MoySklad, recovery BusinessEvent и обычный поток по SOP.

После каждого заказа фиксируются:

- order ID и payment/refund ID;
- сумма заказа, скидка, бонусы и доставка;
- сумма и валюта, подтверждённые платёжным провайдером;
- остаток до и после операции;
- статусы заказа, платежа, доставки и возврата;
- количество доставок webhook и количество доменных эффектов;
- полученные уведомления;
- записи audit trail;
- фактическое время прохождения этапов;
- ссылки на доказательства;
- ошибка, решение и ответственный, если было отклонение.

## Автоматические инварианты

Pilot control автоматически переводит процесс в **STOP**, если обнаружено хотя бы одно из условий:

- один order/payment/refund ID использован в нескольких успешно пройденных сценариях;
- сумма YooKassa отличается от суммы заказа более чем на 0,01;
- валюта провайдера не совпадает с валютой заказа;
- остаток стал отрицательным;
- фактическое изменение остатка не совпало с ожидаемым;
- повторный webhook/callback создал больше одного доменного эффекта;
- критический сценарий отмечен как `fail`.

Сценарий со статусом `pass`, но без обязательных ID, статусов, сумм, остатков или доказательств, не даёт GO и остаётся ошибкой валидации.

## Немедленный STOP пилота

Помимо автоматических инвариантов пилот останавливается при любом из событий:

- возврат денег выполнен без устойчивого локального статуса;
- потерян webhook, notification или business event без видимого retry/review;
- `/ready` возвращает не 200;
- недоступен Admin либо нет audit trail для критического действия;
- обнаружена публикация секрета, персональных данных или внутреннего порта;
- rollback/backup недоступны.

После STOP новые заказы не принимаются до фикса, повторного полного CI и нового решения `make pilot-gate` = **GO**. Запись STOP нельзя «исправить словами»: должны быть устранена первопричина, приложены доказательства и заново пройден затронутый сценарий.

## После 20 заказов

Переход к расширенному пилоту возможен только после одновременного выполнения условий:

- `make pilot-final` возвращает код `0` и решение **GO**;
- количество заказов равно количеству ожидаемых платежей;
- сумма успешных платежей равна сумме оплаченных заказов минус подтверждённые возвраты;
- остатки локальной системы согласованы с MoySklad;
- все review cases имеют владельца и решение;
- критических инцидентов нет, некритические имеют срок исправления;
- ответственные за бизнес, операции и технологию подписали acceptance sign-off.

Исполняемый контроль проверяет структуру доказательств и критические инварианты, но не заменяет реальные операции в Telegram, YooKassa, MoySklad, хранилище, юридическое утверждение документов и подпись ответственных.
