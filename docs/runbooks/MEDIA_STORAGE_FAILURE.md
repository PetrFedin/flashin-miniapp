# Runbook: media object-storage failure

## Trigger

Use this runbook when `/media/upload` fails during S3/R2 upload, database finalization, or compensating object deletion.

## Safety model

- PostgreSQL is authoritative for `MediaAsset` metadata.
- S3/R2 stores the binary object.
- A provider object without a committed `MediaAsset` is an orphan candidate, not a valid catalog asset.
- Never manufacture a successful DB record simply because an object may exist remotely.
- Never delete a storage key that was not generated by the failed operation being investigated.

## Transaction-boundary expectation

For issue #221 and later releases:

1. admin authorization completes;
2. the request SQLAlchemy transaction is ended;
3. object-store `put_object` runs with no active DB transaction;
4. a fresh DB transaction revalidates the admin and persists `MediaAsset` plus audit.

If provider latency correlates with long-lived DB transactions after #221, treat that as a regression.

## Provider timeout or connection failure

1. Record the request/correlation identifier and exact failure class.
2. Do not assume a timeout means the provider rejected the request; the outcome can be ambiguous.
3. Verify whether a `MediaAsset` row exists for the returned/known storage key, if a key is available.
4. Verify the remote object state through the approved storage administration tooling without exposing credentials.
5. If no DB row exists but the object exists, classify it as an orphan candidate.
6. Do not blindly retry an entire user upload as a recovery action unless creating a second independent object is acceptable.

The durable orphan cleanup/review system is tracked by issue #222. Until it is merged, ambiguous orphan candidates require explicit operator handling.

## DB finalize failure after successful upload

The application rolls back the fresh finalize transaction and attempts compensating deletion.

- If deletion succeeds: the failed request remains failed; there should be no committed `MediaAsset` for that object.
- If deletion fails: the application raises an explicit cleanup failure rather than swallowing it. Capture the storage key and escalate for manual verification/recovery. Durable replay/reconciliation remains issue #222.

## Authorization changed during upload

If the admin becomes inactive or loses `media.write` after the provider phase but before DB finalize:

- finalize fails closed with HTTP 403;
- the uploaded object is compensating-deleted;
- no `MediaAsset` should be committed.

Do not bypass the revalidation to make the upload succeed.

## Verification after recovery

Verify all applicable conditions:

- object exists only if a committed `MediaAsset` references it;
- `MediaAsset.storage_key` matches the intended provider object;
- upload audit exists for successful committed media;
- no DB transaction remains open because the provider is slow/unavailable;
- representative media URL resolves through the intended public/CDN path;
- credentials are absent from logs and incident notes.

## Escalation

- Repeated storage/provider outage that blocks catalog operations: SEV2 unless it is part of a broader outage.
- Credential compromise or unauthorized object access: follow the security incident/secret-compromise process and treat severity according to exposure.
- Evidence of data loss or uncontrolled deletion: escalate as a data-integrity incident.

## Related gaps

- #222 — durable cleanup/reconciliation for failed compensating deletes or orphan candidates.
- #223 — synchronous boto3 calls currently block the FastAPI event loop; bounded offload/concurrency is separate.
